# 智维手册——完整面试教程

> 使用方法：先背“30秒版本”和“1分钟版本”，再理解流程与高频追问。面试时不要从技术栈开始念，要先讲业务问题，再讲流程、难点、指标和取舍。

## 一、必须先背会的项目介绍

### 30秒版本

我做的是一个面向产品说明书、操作手册和故障文档的多模态RAG系统。系统使用LangGraph编排知识导入和查询流程：导入阶段通过MinerU解析PDF，结合图片上下文调用视觉模型生成描述，再进行标题级切分、型号识别、BGE-M3向量化，并写入Milvus、Neo4j和MinIO；查询阶段先结合历史会话确认产品型号，再进行向量检索，最终让Qwen基于检索证据生成带`[资料N]`引用的回答。我使用4份官方说明书完成真实入库，并建立32题检索集做消融实验。

### 1分钟版本

这个项目主要解决产品说明书内容多、图片多、型号相似，用户很难快速找到准确操作步骤的问题。管理员上传PDF后，FastAPI先返回`task_id`，后台LangGraph依次完成MinerU解析、图片语义化、文档切分、产品型号识别、BGE-M3向量化、Milvus入库和知识图谱构建。图片会结合所属章节、上文和下文生成语义描述，并上传到MinIO，因此操作图也能被检索和引用。

用户查询时，系统先结合MongoDB历史会话进行Query Rewrite和型号确认，然后根据配置选择Dense快速路径，或者执行Dense/Sparse、HyDE、Web Search、RRF和Reranker完整增强路径。最终Qwen只能根据编号证据回答，并生成`[资料N]`引用。真实实验中，4份说明书共88页形成142个切片；Dense路径Hit@3为93.8%、MRR为0.900、平均检索耗时0.53秒。消融结果说明复杂链路不一定更好，所以我把Dense设为默认路径，把完整链路保留为可配置能力。

### 3分钟展开顺序

1. 业务问题：说明书长、型号相似、图文混合、人工查找效率低。
2. 导入流程：PDF解析 → 图片处理 → 文档切分 → 型号识别 → 向量化 → Milvus → 知识图谱。
3. 查询流程：历史会话 → 型号确认 → 检索 → 融合/精排 → 证据回答。
4. 项目难点：图片缺乏语义、切片过长或过短、型号误匹配、复杂链路延迟高。
5. 真实指标：88页、142个切片、185张有效图片；Hit@3 93.8%，MRR 0.900。
6. 技术取舍：默认Dense，复杂问题再启用HyDE、RRF和Reranker。

## 二、项目解决的业务问题

传统产品资料存在四个问题：

1. **资料分散**：说明书、故障手册、操作步骤和图片分布在多个文件中。
2. **用户表达不标准**：用户可能问“这个怎么充电”“D56C滤芯怎么洗”，而不是使用文档原句。
3. **型号容易混淆**：多个产品都有“无法充电”“吸力下降”等相似章节，直接全库检索容易串型号。
4. **图片无法直接检索**：部件图、安装图和按键图只有视觉信息，普通文本Embedding无法理解。

项目目标不是简单上传文件，而是把非结构化产品资料转成可检索、可关联、可引用的知识，并提供自然语言问答入口。

## 三、总体架构

```text
管理端上传PDF/Markdown
        ↓
FastAPI返回task_id，后台执行
        ↓
LangGraph导入图
        ├─ MinerU：PDF → Markdown
        ├─ VLM：图片 + 标题 + 前后文 → 图片描述
        ├─ MinIO：保存原始图片
        ├─ 文档切分：标题切分、长段拆分、短段合并
        ├─ Qwen：识别产品型号、抽取实体关系
        ├─ BGE-M3：Dense/Sparse向量
        ├─ Milvus：型号、文本切片和实体向量
        └─ Neo4j：实体关系

用户问题 + session_id
        ↓
历史会话 + Query Rewrite + 型号确认
        ↓
默认：Dense快速检索
可选：Hybrid + HyDE + Web → RRF → Reranker
        ↓
Qwen基于编号证据生成答案
        ↓
答案 + [资料N] + 图片链接
```

### 各组件为什么存在

| 组件 | 作用 | 面试表达 |
|---|---|---|
| FastAPI | 上传、状态查询和问答接口 | 提供Web服务和异步任务入口 |
| LangGraph | 编排节点、State和条件路由 | 让长流程显式、可观测、可扩展 |
| MinerU | PDF转Markdown | 保留标题、正文、表格和图片引用 |
| Qwen/VLM | 型号识别、图像描述、答案生成 | 处理非结构化语义任务 |
| BGE-M3 | Dense/Sparse向量 | 同时支持语义和关键词表征 |
| Milvus | 向量检索和标量过滤 | 保存切片向量、型号和元数据 |
| Neo4j | 实体关系存储 | 保存产品、部件、故障、原因和处理关系 |
| MongoDB | 会话与任务信息 | 支持历史对话和任务查询 |
| MinIO | 图片等对象存储 | 保存非结构化资源并生成访问地址 |

## 四、知识导入流程：必须讲清楚

导入图的节点顺序是：

```text
entry_node
   ├─ PDF → pdf_to_md
   └─ Markdown → md_img_node
pdf_to_md
→ md_img_node
→ document_split_node
→ item_name_rec_node
→ bge_embedding_node
→ import_milvus_node
→ kg_node
→ END
```

### 1. EntryNode：文件类型判断

输入主要是：

- `import_file_path`：上传文件路径。
- `file_dir`：本次任务的工作目录。

节点检查文件后缀并更新：

- `is_pdf_read_enabled`
- `is_md_read_enabled`
- `file_title`

LangGraph根据这两个布尔值决定进入`pdf_to_md`还是直接进入图片处理节点。

**面试要点：** 条件边的价值是把文件类型分支写成显式路由，而不是在每个节点中重复判断。

### 2. PdfToMd：PDF解析

该节点调用MinerU把PDF转换成Markdown，输出：

- `md_path`
- `md_content`
- MinerU生成的图片目录

项目还增加了已有Markdown复用机制：任务重试时，如果转换结果已经存在，就不重复执行耗时的PDF解析。

**为什么使用Markdown？**

因为Markdown同时保留了标题层级、正文、表格和图片引用，比直接抽取纯文本更适合后续语义切分和来源追踪。

### 3. MdImageNode：图片语义化

这是多模态导入的核心节点。

处理流程：

```text
遍历images目录
→ 检查图片后缀
→ 根据图片文件名定位Markdown中的引用位置
→ 获取最近标题、上文和下文
→ 图片转Base64
→ 图片 + 上下文提交视觉模型
→ 得到中文图片标题
→ 上传MinIO
→ 用语义标题和远程URL替换原Markdown图片引用
```

图片上下文通常表示为：

```python
(front_title, pre_content, post_content)
```

视觉模型不是只看图片，而是同时接收：

- 文档标题；
- 图片所属章节；
- 图片前后正文；
- 图片本身。

这样可以避免模型把“充电座安装图”只描述成“一个白色设备”。

#### 图片过滤优化

MinerU会提取警告图标、装饰线和小碎片。项目根据图片面积过滤无效对象，并缓存已经生成的图片摘要。

真实结果：

- 原始图片对象：508张；
- 保留有效图片：185张；
- 无效VLM调用减少约63.6%。

**面试回答：为什么需要MinIO？**

数据库不适合直接保存大量图片二进制。MinIO负责对象存储，Markdown、Milvus切片和最终答案只保存URL；这样前端可以展示原图，也便于文件生命周期管理。

### 4. DocumentSplitNode：文档切分

切分目标是在“信息完整”和“检索精确”之间取得平衡。

#### 第一步：按照Markdown标题切分

正则识别一到六级标题：

```python
r"^\s*(#{1,6})\s+(.+)"
```

节点维护标题层级栈，为每段生成：

```python
{
    "title": 当前标题,
    "body": 正文,
    "file_title": 文件标题,
    "parent_title": 父标题,
}
```

代码块中的`#`不会被误判为标题。

#### 第二步：超长章节递归拆分

如果`title + body`超过最大长度，就计算正文可用空间：

```python
title_prefix = f"{title}\n\n"
body_size = max_content_length - len(title_prefix)
```

随后使用`RecursiveCharacterTextSplitter`，分隔符优先级为：

```python
["\n\n", "\n", "。", "！", "？", " ", ""]
```

它会优先在段落和句子边界切分，最后才退化到字符级。

#### 第三步：同源短切片合并

如果当前切片正文小于最小长度，并且下一段具有相同`parent_title`，就合并正文。

这里的“同源”非常重要：不同章节即使都很短，也不能随意合并，否则会把不相关知识放入同一向量。

#### 最终切片结构

```python
{
    "title": "# 维护保养-1",
    "content": "# 维护保养-1\n\n正文内容",
    "file_title": "MC-8D56C",
    "parent_title": "# 维护保养",
    "part": 1,
}
```

**面试回答：为什么不固定每500字切一次？**

固定字符切分会破坏章节语义、操作步骤和表格。标题切分先保证业务结构，再用递归切分处理超长内容，短段只在同一父标题下合并，因此更适合说明书。

### 5. ItemNameRecognition：产品型号识别

节点从文件标题和前几个切片中构建上下文，调用Qwen生成标准产品名称。

选择前部切片的原因是说明书封面、目录和产品简介通常包含品牌与型号，同时可以控制Prompt长度。

识别后做两件事：

1. 将`item_name`写入每个chunk；
2. 使用BGE-M3生成型号的Dense/Sparse向量，写入独立型号集合。

独立型号集合用于查询阶段把“8D56C”“松下8D56C”等用户表达映射到标准名称。

### 6. ChunksEmbeddingNode：批量向量化

Embedding文本不是只有正文，而是：

```text
产品型号
标题
正文
```

这样向量同时包含产品范围和章节语义。

BGE-M3返回：

- Dense向量：连续浮点数组，表达整体语义；
- Sparse向量：`token_id → 权重`字典，强调关键词、型号和故障码。

节点采用批量编码，避免每个切片单独调用模型造成重复开销。

### 7. ImportMilvusNode：向量入库

Milvus集合主要字段包括：

- `chunk_id`：自动生成的主键；
- `dense_vector`：1024维Dense向量；
- `sparse_vector`：Sparse向量；
- `content`、`title`、`parent_title`；
- `file_title`、`item_name`、`part`。

Dense向量使用COSINE相似度，Sparse向量使用IP内积和稀疏倒排索引。

插入成功后，Milvus返回的`chunk_id`会写回chunk，供Neo4j实体、RRF去重和答案来源追踪使用。

### 8. KnowGraphNode：知识图谱构建

Qwen从切片中抽取：

- 产品；
- 部件；
- 故障现象；
- 故障原因；
- 处理步骤；
- 它们之间的关系。

模型输出不稳定，因此必须进行：

1. JSON解析；
2. 实体类型白名单；
3. 关系类型白名单；
4. 空名称清理；
5. 重复实体与关系去重。

清洗后的关系写入Neo4j，实体名称向量可写入Milvus，并通过`source_chunk_id`关联原始证据。

项目还进行了异常隔离：某个切片返回非标准JSON时，只记录该失败切片，不回滚整份文档已经完成的文本、图片和向量数据。

## 五、查询流程：必须讲清楚

### 查询State中的关键字段

| 字段 | 含义 |
|---|---|
| `original_query` | 用户原始问题 |
| `rewritten_query` | 结合历史和型号改写后的完整问题 |
| `item_names` | 已确认的标准产品名称 |
| `embedding_chunks` | 普通检索结果 |
| `hyde_embedding_chunks` | HyDE检索结果 |
| `web_search_docs` | Web搜索结果 |
| `rrf_chunks` | RRF融合结果 |
| `reranked_docs` | Reranker或Dense快速路径的最终证据 |
| `answer` | 最终回答 |
| `sources` | 编号来源列表 |
| `session_id` | 会话标识 |

### 1. ItemNameConfirmNode：型号确认与Query Rewrite

节点读取MongoDB中的最近会话，结合当前问题调用Qwen，返回：

```json
{
  "item_names": ["MC-8D56C"],
  "rewritten_query": "MC-8D56C的过滤网水洗后需要干燥多久？"
}
```

随后把候选型号编码为Dense/Sparse向量，在型号集合中检索标准名称。

#### 型号路由改良

原逻辑对“松下8D56C”“松下CA781”匹配不稳定，并可能把“吸尘器”错误确认成某个产品。

改良包括：

- 从用户名称中抽取含数字的型号Token，例如`8D56C`、`CA781`；
- 在库中只存在唯一包含关系时直接确认；
- 对“吸尘器”“设备”等泛品类词禁止直接确认；
- 多个候选时返回澄清选项。

如果节点已经生成澄清答案，LangGraph直接结束，不进入检索。

### 2. 默认Dense快速路径

默认模式下，`DenseSearchNode`执行：

1. 对`rewritten_query`生成Dense向量；
2. 使用`item_name`构建Milvus标量过滤条件；
3. 只在对应产品的切片中执行COSINE搜索；
4. 返回前10个候选证据；
5. 直接交给答案生成节点。

过滤表达式类似：

```text
item_name in ["Panasonic MC-8D56C 充电式真空吸尘器"]
```

**为什么先过滤型号？**

不同说明书都可能出现“无法充电”“过滤网清理”。如果全库搜索，语义相似但型号错误的切片可能排在前面。型号过滤把问题从“全库检索”变成“指定产品内检索”。

### 3. 完整增强路径

设置：

```env
QUERY_RETRIEVAL_MODE=full
```

会启用三路并行召回：

1. **普通Hybrid检索**：对改写问题生成Dense/Sparse向量后查询Milvus。
2. **HyDE检索**：让Qwen先生成一段说明书风格的假设答案，再对“问题 + 假设文档”向量化。
3. **Web Search**：使用MCP查询外部资料，作为知识库之外的补充。

当前查询图没有接入Neo4j图谱召回，所以面试和简历中不要说“四路并行图谱检索”。Neo4j目前主要用于导入阶段的实体关系存储。

### 4. HyDE为什么可能有效

用户问题通常很短，例如“D56C滤芯怎么洗”，而说明书写法更正式。HyDE先生成可能的文档表达：

```text
关闭吸尘器，取出集尘盒和过滤网组件……
```

再用这段内容检索，可以缩小“问题语言”和“文档语言”的表达差距。

风险是：假设答案可能引入错误词语，而且多一次LLM调用会显著增加延迟，所以不能无条件启用。

### 5. RRF融合

RRF只依赖各路结果的排名，不直接比较不同检索器的原始分数。

公式：

```text
RRF分数 = Σ 权重 / (k + 当前路线中的排名)
```

项目使用`chunk_id`作为同一文档的唯一标识。同一切片被多路召回时，分数会累加，因此排名提升。

例子：

- 切片A在普通检索第1名；
- 切片A在HyDE检索第2名；
- 它会获得两路分数之和。

### 6. BGE Reranker精排

Reranker属于Cross-Encoder，它把“问题—候选文档”作为一对输入，直接计算相关性，比单独计算向量再比较更精细，但计算成本也更高。

节点流程：

```text
RRF候选
→ 构建(query, document)句对
→ BGE-Reranker计算分数
→ 降序排列
→ 检测相邻分数断崖
→ 动态截断
```

动态截断同时考虑绝对分差和相对分差，避免把明显低相关内容全部送入大模型。

### 7. AnswerOutputNode：基于证据回答

节点把候选文档组织成：

```text
[资料1]
标题：故障代码
来源：chunk_id
内容：……

[资料2]
标题：维护保养
来源：chunk_id
内容：……
```

Prompt约束Qwen：

- 只能使用参考资料中的事实；
- 关键结论必须标注`[资料N]`；
- 不得引用不存在的资料编号；
- 资料不足时明确拒答；
- 如果问题需要图片，只能引用证据中的MinIO图片链接。

#### `[资料N]`引用机制怎么解释

`N`不是模型随意生成的编号，而是后端按照候选证据顺序生成的索引。`sources`数组保存编号、标题、chunk_id或URL和分数。模型回答之后，系统还会把“资料1”“参考资料1”等不稳定格式归一化为`[资料1]`，便于前端展示和自动评测。

这是一种可追溯机制，但不等于引用一定正确。还需要校验：

1. 引用编号是否真实存在；
2. 被引用资料是否真的支持对应结论；
3. 答案是否遗漏关键事实。

## 六、Dense、Sparse、RRF、Reranker的区别

### Dense向量

Dense向量是固定维度浮点数组，擅长语义匹配。

例如：

- 查询：“机器吸不动了”；
- 文档：“吸力明显下降”。

虽然词语不同，但语义接近，Dense可能召回。

### Sparse向量

Sparse向量只有少量Token位置有权重，擅长精确关键词。

例如：

- `MC-8D56C`
- `U12`
- “褶状过滤网”

### 为什么生成向量

因为数据库不能直接理解自然语言。Embedding把文本转换成可计算的向量，查询时通过相似度快速找到语义接近的切片。

### RRF与Reranker区别

- RRF融合的是“多路排名”，不读文档深层语义，成本低。
- Reranker重新阅读问题和候选正文，判断相关性，效果潜力更高但成本大。

## 七、真实消融实验：必须会解释

### 数据集

- 4份松下官方说明书；
- 88页；
- 142个切片；
- 32个人工标注检索问题；
- 每题人工绑定相关`chunk_id`；
- 覆盖充电、联网、维护、配件、故障和规格等类别。

### 结果

| 检索方案 | Hit@3 | Recall@5 | MRR | 平均耗时 | P95耗时 |
|---|---:|---:|---:|---:|---:|
| Dense基线 | 93.8% | 100.0% | 0.900 | 0.53s | 0.61s |
| Dense + Sparse | 93.8% | 96.9% | 0.852 | 0.54s | 0.61s |
| Dense/Sparse + HyDE + RRF | 96.9% | 100.0% | 0.852 | 5.31s | 6.59s |
| Dense/Sparse + HyDE + RRF + Reranker | 90.6% | 100.0% | 0.897 | 26.71s | 29.81s |

### 指标含义

- **Hit@3**：前三条中是否至少出现一个相关切片，然后对所有问题求平均。
- **Recall@5**：前五条召回了多少标注相关切片。
- **MRR**：第一个相关切片排名的倒数。第1名为1，第2名为0.5，第4名为0.25。
- **平均耗时**：各题该检索方案端到端检索耗时的平均值。

### 实验结论

1. 型号已经过滤后，Sparse的额外价值不稳定，固定0.5/0.5权重降低了MRR。
2. HyDE+RRF让Hit@3提高约3.1个百分点，但平均延迟约为Dense的10倍。
3. 当前CPU环境下Reranker非常慢，而且Hit@3没有提升。
4. 因此默认使用Dense，完整链路保留为可配置增强模式。

### 面试官问“为什么Reranker反而变差”

可以回答：

> Reranker不是必然提升。当前数据集较小，并且已经先按型号过滤；候选切片较长，包含图片URL和表格文本，本地CPU推理成本也很高。实验中Reranker虽然让MRR接近Dense，但Hit@3下降且延迟显著增加。因此我没有为了堆组件强行上线，而是根据离线指标选择默认Dense。后续可以清洗候选文本、缩短输入、调整TopK，并在独立测试集上重新评估。

## 八、常见面试追问与参考回答

### 1. 为什么使用LangGraph？

导入和查询都不是一次模型调用，而是包含多个有依赖关系的节点、条件分支和共享状态。LangGraph让每个节点输入输出明确，也方便观察任务进行到哪一步、失败后定位具体节点，并支持后续增加新检索路线。

### 2. State是什么？

State是图中所有节点共享的数据协议。节点不直接互相调用，而是读取State中的字段并写回新的字段。例如文档切分节点写入`chunks`，向量化节点读取`chunks`并增加向量，入库节点再读取处理后的结果。

### 3. 为什么图片需要上下文？

很多说明书图片单独看只能识别出设备外观，无法判断它属于安装、清洁还是故障处理。加入章节标题和前后文可以提高描述与业务语义的一致性。

### 4. 为什么切片要保留标题？

标题既提供语义范围，又可以在答案中展示来源。只嵌入正文容易丢失“这段内容属于哪个部件或故障章节”的信息。

### 5. 为什么短切片只能同父标题合并？

短切片信息不足，但跨章节合并会引入语义污染。同一父标题表示它们属于同一业务主题，合并风险更低。

### 6. 为什么产品型号单独建集合？

型号确认发生在正文检索之前。独立集合规模小、查询快，还能把用户简称映射成标准名称，再用标准名称过滤正文集合。

### 7. Milvus和普通数据库有什么区别？

普通数据库擅长精确条件查询，Milvus擅长高维向量近邻搜索。这个项目同时使用向量检索和`item_name`标量过滤。

### 8. Neo4j解决什么问题？

Milvus擅长找相似文本，Neo4j擅长表达实体之间的显式关系，例如“故障现象—可能原因—处理步骤”。当前项目完成了图谱构建，但查询主图尚未接入图谱召回，这是后续扩展点。

### 9. MongoDB保存什么？

主要保存会话历史和任务相关信息。查询节点通过`session_id`读取最近对话，解决“它怎么清洗”这类省略型号的追问。

### 10. 如何避免幻觉？

先通过型号过滤减少错误证据，再要求模型只能基于编号上下文回答；资料不足时拒答；答案引用必须对应真实`sources`编号。更严格的生产方案还需要做引用支持度评测和规则校验。

### 11. Web Search会不会污染答案？

Web结果属于外部不稳定信息，应标记来源并与内部资料分开。项目默认Dense路径不依赖Web；完整模式才把它作为补充。生产环境还应做域名白名单和时效性校验。

### 12. 如何判断项目真的有效？

不能只看答案是否流畅，需要分别评测型号路由、检索Hit@K/MRR、引用合法率、关键事实覆盖和延迟。本项目已经保存逐题JSONL和汇总报告，失败案例也保留用于分析。

### 13. 项目还有哪些不足？

- 文档和评测集规模仍小；
- Neo4j图谱尚未接入查询主图；
- Web搜索质量依赖外部服务；
- CPU Reranker延迟较高；
- 当前指标来自固定离线集，还需要更多品牌和独立测试集。

### 14. 如果继续优化会做什么？

1. 扩展多品牌说明书和独立测试集；
2. 增加基于置信度的自适应检索路由；
3. 清理Reranker输入中的URL和冗余表格；
4. 接入Neo4j图谱召回并重新做消融实验；
5. 增加租户、权限和文档版本过滤。

## 九、不要说错的内容

1. 不要说“Neo4j已经作为第四路并行检索”，当前只完成图谱入库。
2. 不要说“Reranker一定提升效果”，真实实验中它没有提升Hit@3。
3. 不要说“支持所有文档格式”，当前重点验证PDF和Markdown。
4. 不要把32题离线指标说成生产准确率。
5. 不要说系统微调了大模型；项目使用API模型和本地Embedding/Reranker，没有做LLM微调。
6. 不要说必须使用GPU；当前本地BGE模型可在CPU运行，但Reranker延迟较高。
7. 不要说图片存入Milvus；图片本体存MinIO，Milvus保存文本、向量和元数据。
